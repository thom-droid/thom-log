# 예상 작업기간
- 프론트를 제외하고 API 개발부터 테스트까지 완료를 목표로 한다. 
- 평일 작업 시간은 2시간 가량 잡고, 주말은 4시간 정도로 잡는다고 계산한다. 
- 1W = 18H, 4W = 72H
- 현재 기능이 많기 때문에 개발 내용을 조절해야 한다. 
- JPA를 제외한 추가 기능은 없도록 한다. 리팩토링에 집중한다. 쿼리도 복잡하게 짜지 않도록 한다. 

# 서버구성
- 간단하게 진행한다.
- RDBMS : MySQL 8.0
- ORM : JPA (Hibernate)
- Framework : Spring Boot
- Build Tool : Gradle
- Cache : Redis

# 모듈
- core : DB 설정, JPA 및 프로젝트 전반의 설정을 담당하는 모듈
- api : 요청을 수행하여 응답을 반환하는 모듈

# 도메인
- Business : 회사 정보. 회사로 먼저 가입한다.
- User : 회사에 속한 유저 정보. 회사에 속한 유저로 로그인한다. Business와 User는 1:N 관계이다.
- Partner : 회사에 속한 파트너 정보. Business와 Partner는 1:N 관계이다.
- Bank : 은행 정보.
- CardCompany : 카드사 정보.
- TaxInvoice : 세금계산서 정보. Business와 TaxInvoice는 1:N 관계이다.
- CreditCardReceipt : 신용카드 영수증 정보. Business와 CreditCardReceipt는 1:N 관계이다.
- CashReceipt : 현금영수증 정보. Business와 CashReceipt는 1:N 관계이다.
- DepositWithdraw : 입출금 정보. Business와 DepositWithdraw는 1:N 관계이다.
- TransactionVoucher : 전표 정보. Business와 Voucher는 1:N 관계이다. 위 세 가지 도메인은 모두 전표로 변환될 수 있다. 
- GeneralVoucher: 일반전표.
- Item : 각 도메인의 상세 정보. 각 도메인과 1:N 관계이다.
- JournalEntry : 분개 정보. 각 도메인과 1:N 관계이다.

# 도메인별 요구사항 정리
- 생각나는 기능 중에 개발할 내용만 정리한다. 이후에 추가적인 요구사항이 있을 경우, 추가적으로 정리한다.

## 사용자
- Business가 회사 정보를 등록하면, User는 회사에 속해 회사에 로그인할 수 있다.
- User는 회사에 속해 회사의 정보를 조회할 수 있다.
- User에는 대표계정이 있으며, 대표계정은 하위 계정을 둘 수 있다.
- 대표계정만이 회사의 정보를 수정할 수 있다
- 대표계정만이 도메인 관련 정보를 입력하거나 수정할 수 있다. 이 권한은 하위 유저에게도 주어질 수 있으나, 대표계정이 직접 부여해야 한다.

### Business
- Business는 회사명, 사업자번호, 대표자명, 주소, 전화번호, 이메일, 회사 로고로 구성된다.

## 거래 타입 
- 거래 타입은 매입, 매출로 구분된다.
- 11 세금계산서부터 13 현금영수증, 14 신용카드, 15 입출금 정보까지의 거래 타입이 있다.(확인하여 4개 도메인 매입/매출 별 타입 추가 필요)

## 과세구분
- 과세와 면세로 구분된다.

## 거래 정보 (세금계산서, 신용카드, 현금영수증, 입출금 정보)
- 각 도메인은 회사(Business)에 속해 있다.
- 각 도메인은 품목(Item)과 분개(Journal Entry)를 가지고 있다.
- 각 도메인은 전표(Voucher)로 발행될 수 있다.
- 각 도메인에서 전표를 발행하면, 해당 전표는 해당 도메인의 엔티티와 연관관계를 가지며, 회사의 전표 목록에 추가된다.
- 각 도메인은 전표 발행상태에 따라 전표를 발행할 수 있다. 전표 발행상태는 발행가능, 발행 완료, 발행 제외로 나뉜다. 발행 제외, 발행 완료인 경우 수정이 불가하다. 
- 발행 제외는 전표는 발행되지 않은 거래에 대해 수정이나 삭제를 막는 기능이다. 제외를 해제하면 다시 발행 가능상태로 바뀐다.
- 연결된 전표가 있는 도메인은 수정할 수 없다. 수정하려면 전표를 삭제해야 한다.
- 연결된 전표가 삭제되면 해당 도메인은 발행가능 상태로 바뀐다. 반대로 도메인이 삭제되면 전표도 삭제된다.
- 각 도메인은 전표 발행, 수정, 삭제, 조회가 가능해야 한다. 조회는 각각 도메인 번호, 거래처, 발행일로 조회가 가능하며, 조회 시 기본 정렬은 발행일 내림차순 기준으로 한다.
- 각 조회는 매입과 매출이 구분되어 조회된다.
- 수정이 불가한 세금계산서를 제외한 각 도메인은 거래처와 과세/면세 구분을 일괄적으로 수정 가능하다.
- 거래처란 매입인 경우 공급자, 매출인 경우 공급받는자를 의미한다.
- 각 도메인은 과세/면세로도 구분되며, 과세인 경우 세액이 존재하고 면세인 경우 존재하지 않는다.

### 세금계산서
- 세금계산서는 세금계산서 번호, 발행일, 공급자, 공급받는자, 품목, 공급가액, 세액, 합계로 구성된다.
- 세금계산서에 한해서 여러 전표가 연결될 수 있다. 이 경우, 세금계산서는 여러 전표를 가질 수 있다.
- 세금계산서는 한 번 입력되면 수정이 되지 않는다. 삭제만 가능하다.

### 현금영수증
- 현금영수증은 현금영수증 번호, 발행일, 공급자, 공급받는자, 품목, 공급가액, 세액, 합계로 구성된다.

### 신용카드
- 신용카드 영수증은 신용카드 번호, 발행일, 공급자, 공급받는자, 품목, 공급가액, 세액, 수수료, 합계로 구성된다.
- 신용카드는 거래 내역을 거래타입과 카드사가 같은 경우 병합할 수 있다. 병합된 내역은 다시 분리할 수 있다. 병합은 전표 발행 상태가 발행가능인 경우만 가능하다.

### 입출금정보
- 입출금정보는 입출금 번호, 입출금일, 거래은행, 입금액, 출금액, 잔액으로 구성된다.
- 입출금정보는 일반전표로 발행된다.

## 전표
- 전표는 전표 번호, 발행일, 거래처, 품목, 공급가액, 세액, 수수료, 합계, 관련 거래 구분, 관련 거래 번호로 구성된다.
- 거래 내역에서 발행되므로, 품목과 분개를 똑같이 가진다.
- 전표발행은 같은 도메인에 한해 단건, 다건 발행이 가능하다.
- 매입매출이 존재하는 세금계산서, 현금영수증, 신용카드에 대해서 발행되는 전표이다.
- 자동 발행은 거래 내역을 그대로 전표로 발행하는 기능이다. 거래 내역에서 기능을 호출한다.
- 수기 작성은 직접 전표를 작성한다. 

## 일반전표
- 일반전표는 전표와 거의 동일하다. 다만, 품목이 없다.
- 일반전표는 입출금정보에서 발행된다.

## 품목
- 품목은 품목 번호, 품목명, 단가, 수량, 공급가액, 세액, 합계로 구성된다.

## 분개
- 분개는 분개 번호, 차대변, 금액, 분개명으로 구성된다.
- 분개는 기본 분개가 존재하며, 과세 면세에 따라 세액이 달라진다.
