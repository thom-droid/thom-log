- Deadlock happens when **Two transactions wait on each other forever.**


# How To Reproduce

Tx1:
```sql
SELECT * FROM seat WHERE id = 1 FOR UPDATE;
```

this will acquire a lock for the row.

Tx2:
```sql
SELECT * FROM seat WHERE id = 2 FOR UPDATE;
```

Tx2 will also get a lock for the row of which id is 2.

Tx1:
```sql
SELECT * FROM seat WHERE id = 2 FOR UPDATE;
```

And Tx1 attempts  to get a lock for the row id 2 but Tx2 blocks it, so Tx1 waits for Tx2.

Tx2:
```sql
SELECT * FROM seat WHERE id = 1 FOR UPDATE;
```

Tx2 also wants to have a access to the row id 2 but Tx1 is holding, so it has to wait. 
But none of them can proceed since they are waiting for each other to release the lock. 

```
ERROR: deadlock detected.
```

---

# What's Dangerous 
because it
- Wastes time
- Aborts transactions
- Causes retries
- And reduces throughput.

---

# Golden Rule to Prevent the deadlock

> always **lock rows in a consistent(deterministic) order**.

instead of 
```
Tx1: seat1 -> seat2
Tx2: seat2 -> seat1
```

always
```
seat1 -> seat2
```

So make the both transaction do the lock in order as below:
```sql
SELECT * FROM seat
WHERE id IN (1,2)
ORDER BY id
FOR UPDATE;
```

because the row id 1,2  now are locked and the second transaction has to wait for the first.

---
# Why Atomic Updates Rarely Deadlock

Because atomic updates usually touch one row;

deadlock is more likely to occur when multiple rows and multiple tables are updated in a different order.
