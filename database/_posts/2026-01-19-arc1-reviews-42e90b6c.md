# CheckList

## ✅ ARC 1 — Evaluation Checklist

### Database & Transactions
- [x] I can explain MVCC using **row versions and snapshots**
	- MVCC allows concurrent reads and writes without read locks by deciding row visibility at read time.
	- Updates create a new tuple and invalidate the old one (insert + invalidate), with cleanup handled later by vacuum (row versioning).
	- it's enabled by row versioning, which in transaction rows are not immediately updated or deleted; new tuple representing the row is added and the old version marked as the target of delete (so update is delete + insert and expensive!).
	- And the versioned rows' information is used for taking snapshots when transaction starts or during a transaction depending on isolation level, which determines which rows are visible to the snapshot.
	- Row visibility is determined by comparing tuple xmin/xmax with the transaction snapshot.
- [x] I can predict visibility in READ COMMITTED and REPEATABLE READ
	- in READ COMMITTED, snapshot are taken per statement. So if the same statement executed again in between the transactions has committed, then you might see the different result.
	- In REPEATABLE READ, snapshots are taken per transaction, meaning from the start of the transaction it always sees the same, first created snapshot in the transaction. 
- [x] I understand why phantom reads still exist
	- it's because in some REPEATABLE READ implementation (like InnoDB) it only protects (locks) the rows, not the range, which means the inserted rows are not locked, so not in the range.
	- whereas PostgreSQL logically makes the rows invisible comparing snapshot and row versions (snapshot locking)
- [x] I know why readers and writers still block each other
	- Readers don't need to block writers under MVCC because they can read from the snapshot.
	- Writers block writers because only one transaction can own the right to create the next version of a row. (And database must know which transaction is visible successor of the row)
